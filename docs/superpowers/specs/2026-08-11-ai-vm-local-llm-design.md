# Local LLM VM for agentic coding — design

## Goal

Stand up a VM on `workstation` (the Proxmox host holding the RTX A5000) that
runs a local LLM inference server plus the Hermes agentic-coding CLI, using
the full 24GB (24Q) vGPU slice. Keep the deployment flexible enough that it
can later be handed off to `gpu-manager` (dynamic GPU claims) without a
redesign, but do not wire that integration up now.

## Non-goals

- Building/deploying `gpu-manager` itself (it's not deployed anywhere yet;
  only its example config already anticipates this exact use case).
- Concurrent GPU sharing between `ai-vm` and `gaming`. The A5000 only permits
  one homogeneous vGPU slice size across the whole card, so with `gaming`
  already claiming the full 24Q slice, the two VMs are mutually exclusive.
  Making that non-exclusive is exactly what `gpu-manager`'s claim/preempt
  model is for, later.
- Exposing the inference API outside the LAN/Netbird network.

## Architecture

```
workstation (Proxmox host, RTX A5000, SR-IOV/vGPU)
├── gaming (VM 111)   — existing, claims full 24Q slice when running
└── ai-vm  (new VM)   — claims full 24Q slice when running
        ├── Ollama (systemd service, binds all interfaces)
        │     ├── Qwen3.6-27B  (Q4)
        │     └── Devstral-Small-2-24B (Q4)
        └── Hermes agent CLI (runs as the `llm` user, talks to
              Ollama's OpenAI-compatible API on localhost)
```

Only one of `gaming` / `ai-vm` can be running at a time. Stopping the running
one releases its mdev automatically (Proxmox tears it down on VM stop); no
manual mdev reset is needed. This was confirmed live: `creatable_vgpu_types`
on a free VF is empty while any mdev is active elsewhere on the card, and the
24Q profile becomes creatable again as soon as the active VM stops.

## VM provisioning (OpenTofu)

Add a new VM under `workstation.vms` in
`tofu/deployments/edholm/configurations.tfvars`, alongside the existing
`gaming` block:

- **Name**: `ai-vm` — matches the name already used in `gpu-manager`'s
  `config.example.yaml` (`ai-vm: {vmid: 300, tier: ai}`), so no renaming is
  needed if/when that project is deployed.
- **Clone**: `ubuntu-2604-base` (same base image as `gaming`).
- **Sizing**: 8 cores, 32GB RAM, 150GB disk. Inference is GPU-bound; the
  larger disk just gives headroom for multiple model files (each model is
  roughly 15-18GB at Q4).
- **`pci_devices`**: one entry, `mapping_id = "RTX-A5000"`,
  `vgpu_slice_gb = 24`, `pcie = true`, `primary_gpu = false`,
  `rombar = false` — identical shape to the gaming VM's block, since this VM
  is also a headless render node (no emulated display needed as primary).
- **`roles`**: `[{ name = "llm" }]` (see below).
- No `mounts` — model weights live on the VM's own disk, not shared storage.
  Unlike game libraries, models aren't meant to be shared read/write across
  VMs, and only one VM using the GPU is ever running at a time anyway.

`ansible/playbooks/edholm.yaml` and `ansible/inventory/edholm.yaml` are
generated by the `ansible-wiring` tofu module (gitignored) — no manual edits
there; `tofu apply` regenerates them from `configurations.tfvars`.

### Manual step before first apply

`gaming` (VM 111) must be stopped before `ai-vm` can start, since the 24Q
slice can't be created while `gaming` holds it:

```
ssh root@workstation.netbird.cloud "qm shutdown 111"
```

## Driver refactor: shared vGPU guest driver + licensing

`ansible/roles/gaming/tasks/nvidia-guest.yaml` and `nvlts-license.yaml`
(plus the vendored `files/nvlts` binary and
`templates/nvlts-generate-license.sh.j2` / `gridd-guest.conf.j2`) install the
vGPU guest driver and forge an offline nvlts license. None of this is
gaming-specific — `ai-vm` needs the identical driver + licensing flow.

Move these tasks and their files/templates into the `drivers` role as
shared guest-side tasks (e.g. `drivers/tasks/nvidia-guest.yaml` +
`drivers/tasks/nvlts-license.yaml`), along with the vars they depend on
that currently live in `gaming/defaults/main.yaml`
(`nvlts_repo_url`, `nvlts_vendored_commit`, `nvlts_fallback_driver_version`,
`vgpu_product_name`, `vgpu_feature_name`, `vgpu_feature_version`,
`vgpu_feature_type`) — these describe the vGPU license product, not
anything gaming-specific.

Update `gaming/tasks/main.yaml` to include the driver setup from the
`drivers` role instead of its own copy. The new `llm` role includes the same
shared tasks. No behavior change for the existing `gaming` role — this is a
pure relocation.

## New ansible role: `llm`

`ansible/roles/llm/`, applied to `ai-vm`:

1. Base packages (curl, git, htop, jq, build-essential, qemu-guest-agent).
2. Dedicated `llm` system user (own account, not `gamer` — this VM has no
   relationship to the gaming role's user/session model).
3. Enable `qemu-guest-agent`.
4. vGPU guest driver + nvlts licensing, via the shared `drivers` role tasks
   (`gpu_type: nvidia_vgpu`).
5. **Ollama**: install via the official install script, run as a systemd
   service. `OLLAMA_HOST` set to bind all interfaces (`0.0.0.0:11434`), not
   just localhost — so the OpenAI-compatible API is reachable from the
   LAN/Netbird for future clients (other machines, or `gpu-manager` health
   checks later), not only from Hermes on-box.
6. **Model pull**: a role variable listing models to `ollama pull`, defaulting
   to:
   ```yaml
   llm_ollama_models:
     - "qwen3.6:27b-q4_K_M"      # placeholder tag — verify exact tag on first deploy
     - "devstral-small2:24b-q4_K_M"  # placeholder tag — verify exact tag on first deploy
   ```
   Run as an async task (these are multi-GB downloads). Kept as a plain list
   variable specifically so models can be added/swapped without touching
   role logic.
7. **Hermes agent CLI**: install via the official `install.sh` as the `llm`
   user (bundles its own `uv`/Python 3.11/Node — no system Python/Node
   dependency to manage). Template a Hermes config pointing its default
   provider at `http://localhost:11434/v1` (Ollama's OpenAI-compatible
   endpoint) with the first entry of `llm_ollama_models` as the default
   model.

   **Caveat**: Hermes' on-disk config schema for custom OpenAI-compatible
   providers isn't fully documented publicly. The templated config is a
   best-effort based on available docs. Treat first `hermes` run on the VM
   as a verification step — if the wizard still prompts for provider
   selection despite the pre-seeded config, that's expected and just needs
   confirming once (no external account/credentials involved, since we're
   using a local custom endpoint, not Nous Portal/OpenRouter/OpenAI).

## Future `gpu-manager` integration (not built now)

Nothing above needs to change for this later:
- `ai-vm`'s name already matches `gpu-manager`'s example (`ai-vm`, tier `ai`).
- The `llm` role's Ollama setup is orthogonal to *how* the VM's GPU slice
  gets assigned (static tofu `pci_devices` today vs. a dynamic
  `gpu-manager` claim later) — the guest OS doesn't know or care which
  managed it.
- When `gpu-manager` is deployed, the tofu `pci_devices` block on `ai-vm`
  (and `gaming`) would move from static assignment to being managed by
  `gpu-manager`'s reconcile loop instead — a tofu/host-config change, not
  a guest role change.

## Verification plan

- `tofu plan`/`apply` creates `ai-vm` cleanly after `gaming` is stopped.
- `nvidia-smi` inside `ai-vm` shows the licensed 24Q slice.
- `ollama list` shows both pulled models; `curl localhost:11434/v1/models`
  responds.
- `hermes` runs interactively as the `llm` user and can complete a basic
  coding task against each model via Ollama.
- Stopping `ai-vm` and starting `gaming` again works without manual
  intervention (mdev teardown/recreate is automatic).
